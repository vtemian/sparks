# The queue: push, build, run, walk away

Status: proposed
Repos: `sparks` (submit, queue, runner) and `sparkup` (the service that hosts it)

## The problem, stated as the person hitting it states it

> I need the queue so I don't have to leave my laptop here.

Today a training run is `scripts/spark.sh run CMD`, which is `ssh box "cd ~/bbm && CMD"`
in the foreground. Close the laptop, the SSH session dies, SIGHUP kills the
training. Nothing on the box is set up to hold a long job: `Linger=no` for both
accounts, so even a systemd user service would be torn down at logout.

The wanted shape, in the words that specified it: *as easy as possible and as
isolated as possible — something similar to a push of the changes, and on the box
the image is built and run.*

So: one command from the laptop, code goes over, the box builds an image, the job
waits its turn, runs isolated with the GPU, and the laptop is free the moment the
command returns.

## What sparks may and may not know

sparks is a framework several projects use. It knows about *jobs*, never about
bbm. Concretely, the contract with a project is one line long:

> Your project directory contains a `Dockerfile`. sparks builds it and runs the
> command you gave against the resulting image.

That is the whole coupling. No project name, no assumed layout, no
`~/bbm`. A project that wants a different base image, a different package
manager or a different entrypoint says so in its own Dockerfile.

## Flow

From the project directory on the laptop:

```sh
sparks submit --name e0 -- python -m bbm_train.run_e0
```

1. **Ship.** The client rsyncs the project to
   `$SHARED/spool/<job-id>/context/`, honouring `.dockerignore`. rsync rather
   than `git push` deliberately: experiments run with uncommitted edits, and
   forcing a commit before every run is the opposite of "as easy as possible".
   Where a `.git` exists the SHA and a dirty flag are recorded, so provenance is
   captured without being demanded.
2. **Enqueue.** The client writes `job.json` beside the context, `tmp` then
   `rename`, so a job becomes visible only once complete. The file is owned by
   the submitter, which is what later decides who the container runs as.
3. **Exit.** The client prints the job id and returns. The laptop is free.
4. **Build.** The queue picks the oldest queued job, builds the context, and
   records the resulting image digest. The digest is the reproducibility story
   this project has never had: `~/bbm` on the box is an rsynced copy with no
   `.git`, so `git_sha` records nothing today.
5. **Run.** One job at a time, wrapped by `sparks run`, which already owns the
   run directory, the energy delta, `output.log`, `summary.json`, the index
   rebuild and a faithful exit code.
6. **Report.** Terminal state written, notification sent, queue metrics
   republished.

## Design decisions, and why

### The queue is a container, and it holds the Docker socket

Every service sparkup runs is containerised, with one documented exception: the
exporters are host systemd units because a containerised node-exporter needs
`/:/host:ro,rslave`, and that mount makes the filesystem collector recurse every
Docker overlay and hang. The queue has no such reason, so it is a compose service
next to Prometheus and Grafana.

It needs `/var/run/docker.sock` to build and run job containers, and that socket
is root-equivalent on the host. **That is the whole security surface of this
design**, so the queue must never run what a job file merely asks for:

- The container runs as the **submitter's uid:gid, taken from `stat()` on the
  job file**, never from a field inside it. You cannot create a file owned by
  somebody else, so that identity cannot be forged. `fs.protected_hardlinks=1`
  on this box closes the link-to-someone-else's-file trick.
- Mounts are chosen by the queue, not the job: the shared tree and the run
  directory. A job that could name its own `-v` could mount `/` and be root.
- No `--privileged`, no `--user 0`, no `--pid=host`, no added capabilities.
- The spool directory is `2775` **plus the sticky bit**, so a group member
  cannot delete or replace a colleague's queued job.

Honest limit: `docker build` runs the project's Dockerfile on the host daemon,
and a Dockerfile is code. Both accounts here already have `sudo` and are in the
`docker` group, so this grants them nothing they lack — but it means the queue is
a convenience boundary between colleagues, not a security boundary against a
hostile submitter. Written down so nobody later mistakes it for the latter.

### What sparkup has to provide

The queue is sparks' service, so it belongs to sparkup's `sparks` role rather
than to `monitoring`, as its own compose project. The role grows:

- the compose service, with `/var/run/docker.sock`, the shared tree, `/sys:ro`
  and `--gpus all` — the last two because `sparks run` reads hwmon and NVML from
  inside this container
- `/etc/passwd` and `/etc/group` mounted read-only, so a numeric uid taken from
  a job file resolves to the name that goes in the run record. Without this the
  container has no idea who `1001` is
- `$SHARED/queue`, setgid to the shared group **and sticky**, so a group member
  can submit but cannot delete a colleague's job directory
- `queue_dir` added to `/etc/sparks/box.toml`, so the client discovers the spool
  the same way it already discovers everything else about the box
- the queue image pinned by digest, alongside `prometheus_image` and
  `grafana_image`

### Ordering is global FIFO, enforced by one runner

A single queue container processes everything, so exclusivity is structural and
ordering is simply submit time. This is where the container model beats the
per-user systemd design considered first: with one privileged runner able to
`--user` into anybody, there is no need for one runner per account and no
cross-user lock to make fair.

### `sparks run` wraps `docker run`, from inside the queue

The alternative — `sparks run` as the entrypoint *inside* every training
container — would force every project's image to contain sparks. That fails the
"as easy as possible" test for whoever writes the Dockerfile.

So the queue container runs `sparks run -- docker run ...`, and the training
container stays a plain image that knows nothing about sparks. The cost is that
the queue container needs what the energy sampler reads: `/sys` mounted
read-only for hwmon, and `--gpus all` for NVML. Both are read-only uses.

Note the child of `sparks run` is then the `docker run` *client*, so the
supervisor's signal forwarding and exit-code propagation must be checked against
a container child rather than assumed — `docker run` forwards SIGTERM to PID 1 in
the container and returns its exit status, but `--init` and stop-timeout
behaviour need proving in a live test, not reasoning.

### The queue image comes from a registry, pinned by digest

sparks has no CI, no Dockerfile and no published image today, and sparkup pins
`prom/prometheus:v3.13.2` and `grafana/grafana:13.1.1` by tag. Three ways to get
a queue image onto the box:

1. **GitHub Actions in sparks publishes to ghcr.io; sparkup pins the digest.**
   Matches how every other image on the box arrives, keeps provisioning offline,
   and gives the queue a version independent of whoever last ran `make deploy`.
2. Build on the box from a git clone at a pinned ref. Makes converge depend on
   reaching a git remote, which the alert-rules decision deliberately avoided.
3. Build on the box from whatever `make deploy` rsynced. Puts a user's working
   copy in the provisioning path, which is the layering violation this whole
   line of work has been undoing.

Going with 1. It is the only one that leaves the box describable without knowing
who touched it last.

## The job record

One directory per job under `$SHARED/queue/<job-id>/`, where the id reuses
`run.new_run_id` — `20260806-104500-vlad-e0` — so jobs sort chronologically by
name, FIFO needs no separate ordering key, and a job id is visibly related to the
run id it produces.

Inside it, **two files with one writer each**, which is what makes concurrent
access safe without a lock on the hot path:

- `job.json` — the submission, written once by the client and never touched
  again: name, command, submitted time, git provenance, `retry_of`.
- `state.json` — everything that changes, written only by the runner: state,
  image digest, `run_id`, container id, timestamps, exit code, failure reason.

Plus `context/` (the build context), `build.log`, and `requests/`.

**Lifecycle operations go through `requests/`, not through direct edits.** A
client asking to cancel or abort drops a file there; the runner acts on it and is
the only thing that ever writes state. This is not ceremony — it is what makes the
ownership check trustworthy. The runner compares `stat().st_uid` of the request
file against the job's owner, and since you cannot create a file owned by somebody
else, the identity cannot be forged. The same trick already decides which uid the
job's container runs as.

The four operations, and what each means:

| | applies to | what happens |
|---|---|---|
| `cancel` | queued | dropped before it ever builds |
| `abort` | building or running | SIGTERM to the supervisor, which is the path `sparks run` already handles and records as `cancelled` |
| `retry` | any terminal job | a new job id, the same context hardlinked with `cp -al`, `retry_of` recorded |
| `remove` | any terminal job | the directory goes, freeing the context |

`retry` is a client-side re-submit rather than a runner operation, so a retried
job is an ordinary job with provenance — not a second attempt hidden inside the
first, which would make "what did this job do" ambiguous.

States are `queued`, `building`, `running`, then one of `finished`, `failed`,
`cancelled`, `aborted`. These are the *job's* states and are deliberately not
`summary.STATUSES`: a job can fail at build time, having produced no run at all,
and no run status can express that.

## Observability

`sparks_queue.prom`, written by the runner into the same textfile directory the
run index already uses, so it needs no new scrape target and survives losing the
TSDB:

- `sparks_queue_job_info{job_id, name, user, state, image}` — the queue as a
  table, which is what "what is running and what is pending" wants
- `sparks_queue_depth{state}` — the number to graph and alert on
- `sparks_queue_job_submitted_timestamp_seconds` and `..._started_...` — wait and
  runtime, left to PromQL rather than precomputed
- `sparks_queue_runner_heartbeat_timestamp_seconds` — the runner saying it is
  alive, which is the only thing that can distinguish "nothing queued" from
  "nothing is picking anything up"

Cardinality is bounded by publishing every non-terminal job but only recently
terminal ones. Finished jobs are not history — their runs are already in
`sparks_runs.prom` permanently — so nothing is lost by ageing them out here.

That heartbeat earns a new rule in `alerts/sparks.yml`: jobs queued, none
running, runner silent. A queue that has quietly stopped accepting work while
looking fine is precisely the failure mode that file exists for.

## Slices

**Slice A — off the laptop.** `sparks submit`, `sparks queue`, `sparks cancel`,
`sparks abort`, `sparks retry`, `sparks remove`, the job record above, the queue
container, build-and-run, terminal states, and `sparks_queue.prom` with the
overview panel and the stuck-runner alert. Reuses `sparks run` wholesale. Done
when a job survives closing the laptop and the queue is legible in Grafana.

**Slice B — audible.** Notification on terminal state.

**Slice C — the rough edges.** Tailing a running log from the laptop, retention
of build contexts, and the OOM detection that `process.py` already implements but
nothing reaches, now that jobs run in a cgroup with a `memory` controller.

## What Slice A actually cost, and what it taught

Built and tested: `spool.py` (the job record), `runner.py` (ordering, lifecycle,
authorisation, reconciliation), `engine.py` (Docker), `client.py` and the CLI
verbs, queue metrics in `index.py`, the `Dockerfile` and its publishing workflow,
sparkup's `queue` role, two alert rules and four dashboard panels.

Three bugs survived a full unit suite and were caught only by running the thing
against a real daemon. All three are now pinned by tests:

**Dropping privilege is not always possible.** `Popen(user=...)` is EPERM unless
you are root. The runner is root in its container, so the unit tests' assumption
held everywhere except on a laptop -- where it crashed outright rather than
degrading. It now checks instead of attempting, and warns when it cannot record
a run under its true owner.

**A crash mid-job stops the queue permanently.** That first crash left a job
recorded `running`, which `next_queued` skips forever. The queue would accept
work and silently never run any of it, with a green container and no error
anywhere. `Runner.reconcile()` now runs at startup: there is exactly one runner
and it is the one starting, so anything mid-flight is orphaned by definition. It
is marked failed with a reason and its container removed -- not requeued, because
re-running half-completed work is the submitter's decision.

**A global flag after a subcommand is a hard argparse error.** `sparks --url X
run` is valid and `sparks run --url X` is not, and the engine built the second.
The job failed with exit 2 and the explanation went to a log file nobody would
think to open. This is the argument for the command being a pure function: the
test that pins the flag's position is worth more than the one that runs it.

A fourth, quieter one came from reading the record rather than from a failure:
every queued run was recording *sparks'* own commit as the training code's,
because `git_sha()` reads the working directory and the runner's is the
framework's. A wrong answer that looks exactly like a right one.

## Acceptance

- `sparks submit` returns in seconds; killing the laptop's network immediately
  after does not affect the run.
- Two jobs submitted back to back run one after the other, never concurrently,
  in submit order, across two different accounts.
- A job submitted by `marius` runs as `marius` and writes a run directory he
  owns; `vlad` cannot cancel or overwrite it.
- A job whose Dockerfile fails to build reaches `failed` with the build log
  kept, and does not block the job behind it.
- The queue survives a box reboot with jobs still queued.
- `count(sparks_run_info)` grows by exactly one per finished job, and the
  container's exit code is the run's recorded status.
- A queued job cancels, a running job aborts within its grace period and is
  recorded `cancelled` with a real partial run, and a terminal job retries into a
  new job carrying `retry_of`.
- `sparks queue` and the Grafana panel agree with each other and with `docker
  ps`, and stopping the runner fires the stuck-queue alert with jobs waiting.

## Open

**The client on the box is the runner's own image.** `/usr/local/bin/sparks` is
a wrapper that runs the queue image as the calling user, rather than an installed
package. It keeps sparkup's rule that the box does not install sparks as a
library, and it makes client-runner version skew impossible -- they are the same
build reading the same files. The cost is that `sparks run` cannot work through
it, since it would launch training inside the client's container; the wrapper
says so and points at `pip install`.

**Where notifications go.** Email, a Slack/Discord webhook, or a phone push all
cost about the same to build; the channel decides the dependency and the secret
sparkup has to hold. Unanswered, so Slice B assumes a single outbound webhook URL
provisioned as box config, which every one of those can be adapted to.

**bbm has no Dockerfile.** Not sparks' problem by design, but it is a
prerequisite for the first real end-to-end test, so Slice A should be proven with
a throwaway image first.
